# Research: Query Editor Component (Monaco Editor vs CodeMirror 6)

## Summary

Both editors already ship a generic SQL grammar/dialect as a starting point for the T-SQL-ish side (Monaco's `basic-languages` bundles `sql`, `mysql`, `pgsql`, `redshift`; CodeMirror's `@codemirror/lang-sql` ships `MSSQL`, `PostgreSQL`, `MySQL`, `SQLite`, etc. dialects) — neither ships Cosmos DB's "SQL for NoSQL" dialect, and for *highlighting-grade* support of that dialect the real work on both sides is closer to "define a keyword/builtin/type list" than "write a parser from scratch," because both editors expose a declarative dialect-definition API (Monaco's Monarch tokenizer config; CodeMirror's `SQLDialect.define({keywords, builtin, types, ...})`) built for exactly this. A full Lezer grammar is only needed if structural features beyond highlighting are wanted later (clause-aware folding, semantic lint, AST-driven completion). Completion-provider APIs are comparably mature on both sides, with CodeMirror's `@codemirror/lang-sql` additionally shipping a ready-made `schemaCompletionSource()` for metadata-driven completion that Monaco has no equivalent of (Monaco's path is entirely hand-rolled via `registerCompletionItemProvider`). Monaco ships dramatically more out of the box — most notably a **minimap** and a full **command-palette UI**, neither of which CodeMirror's core packages have any equivalent for — at the cost of being far harder to trim; CodeMirror ships a much smaller `basicSetup` (no minimap, no command-palette UI, keymap-driven search/fold/history) assembled from separate `@codemirror/*` packages. In an Electron context, Monaco's multi-MB footprint is credibly "noise" against Chromium's installed-size baseline, but it introduces a real, documented class of integration friction (web-worker wiring, AMD-vs-ESM loader behavior under `file://`, asar packaging of worker scripts) that CodeMirror — which needs no web workers at all — simply does not have. Both core projects (Microsoft's `monaco-editor`; Marijn Haverbeke's CodeMirror 6) show active, current maintenance through 2026; the one concrete staleness signal found is in a *wrapper* package, `@monaco-editor/react` (last published Feb 2025, ~20 months stale as of this research), not in Monaco itself.

## 1. Custom language/grammar support for a non-standard query language

**Baseline both editors already provide, confirmed via package inspection (high confidence):**
- Monaco's bundled `basic-languages` set includes `sql`, `mysql`, `pgsql`, and `redshift` Monarch tokenizers (contributed originally by TeamSQL, per a 2018-era `microsoft/monaco-languages` PR; MSSQL support predates that PR). Third-party bundles (`monaco-sql-languages` by DTStack, `@popsql/monaco-sql-languages`) extend this further (Hive, Spark, Flink, Trino, Snowflake, BigQuery) but are not part of core Monaco.
- CodeMirror's `@codemirror/lang-sql` (npm, v6.10.0 as of this research) exports built-in dialects `StandardSQL`, `PostgreSQL`, `MySQL`, `MariaSQL`, `MSSQL`, `SQLite`, `Cassandra`, and `PLSQL`, each constructed via `SQLDialect.define(spec)`.
- Neither ships a Cosmos DB NoSQL dialect. Both would need one authored for QueryForge.

**Correction to the task's framing:** Cosmos DB's NoSQL dialect does have a `JOIN` clause — it performs intra-document array-flattening (joining a document to elements of its own nested array), not cross-container joins. This is a one-line correction, not a substantive change to the keyword-list scope.

**The two extension models, as documented:**
- **Monaco / Monarch**: `monaco.languages.register` + `monaco.languages.setMonarchTokensProvider` takes an `IMonarchLanguage` object — a declarative, regex/state-machine-based stream tokenizer with a `tokenizer` map of named states to arrays of `[regex, action]` rules. It is permissive to the point of messiness: per a developer who ported a Monarch grammar to CodeMirror, "Monarch enthusiastically allows you to do things that Lezer restricts" (input backup, rematching, phantom states, lookbehind), producing a flat token stream for coloring, not a real syntax tree.
- **CodeMirror 6 / Lezer**: a true incremental parser-generator. The general-purpose path is writing a `.grammar` file compiled by `lezer-generator` into parse tables, then attaching highlighting/folding/indentation via node-specific props (`styleTags`, etc.) on an extended copy of the parser — real work, and CodeMirror's own example docs note it's the more rigorous but heavier-weight of three available paths (the others being a CodeMirror-5-style stream parser — "mostly just a tokenizer," similar in spirit to Monarch — or a fully custom hand-written parser, recommended only for special cases like Markdown).
- **But for a SQL-family dialect specifically, neither editor forces the heavy path.** CodeMirror's `SQLDialect.define()` takes plain space-separated strings for `keywords`, `builtin`, and `types`, plus toggles for quoting/comment/escape conventions (`identifierQuotes`, `doubleQuotedStrings`, `backslashEscapes`, etc.) — i.e., defining a new SQL-ish dialect is realistically a ~20-50 line config object, the same order of effort as a Monarch tokenizer definition, not a from-scratch Lezer grammar. A full custom Lezer grammar would only be needed if QueryForge wants structural features beyond coloring (clause-aware code folding, AST-based linting/completion) that go past what the shared SQL grammar's token stream can give.

**Net:** for *highlighting-grade* support of a Cosmos NoSQL dialect and a T-SQL-ish dialect, the realistic lift is comparable on both editors — both reduce to listing keywords/builtins against an existing SQL-shaped grammar/dialect skeleton. The commonly cited "Monarch is easy, Lezer is a steep compiler-theory investment" framing is accurate only if deeper structural parsing is the goal; for keyword-list-level dialect definition it overstates CodeMirror's cost. Confidence: **high** for the API shapes and built-in dialect lists (verified directly against package docs/source); **medium** for the practical effort estimate ("~20-50 lines"), which is inferred from the API shape rather than measured by building it.

## 2. Autocomplete/completion provider APIs

**Monaco:** `monaco.languages.registerCompletionItemProvider(languageId, { provideCompletionItems })` is the only path — SQL is not a built-in-with-completion language in Monaco (setting the language to `sql` only gets tokenizing/coloring). The API supports async `provideCompletionItems` (so a backend/API call mid-typing is viable), `triggerCharacters`, and range-scoped `CompletionItem`s with `kind`/`detail`/`insertText`. Real-world patterns documented: merge static keyword completions with dynamically-fetched table/column names into one `suggestions` array; dispose and re-register the provider when the active connection/schema changes (a known pain point is duplicate suggestions if you don't dispose the old provider first); cache schema metadata locally per connection to avoid re-fetching on every keystroke. This is all hand-rolled — there is no built-in "schema completion" helper in Monaco itself.

**CodeMirror 6:** `@codemirror/autocomplete`'s `CompletionSource` is a function taking a `CompletionContext` and returning a `CompletionResult` (or a `Promise` of one) — confirmed directly by the maintainer (Marijn) on the CodeMirror forum: "completion sources can be any asynchronous function, and can read the editor state." Notably, `@codemirror/lang-sql` ships a ready-made `schemaCompletionSource({schema, ...})` helper specifically for database table/column completion — a prebuilt counterpart to what Monaco developers hand-roll. One documented limitation: only one in-flight query per source is allowed (a debounced re-wrap pattern is the forum-recommended workaround for high-frequency schema lookups), and the completion tooltip's rendering itself is not overridable — you work within its default display. For context-aware completion (e.g., only suggesting columns after `FROM <table>.`), CodeMirror's docs note it's often useful to inspect the syntax tree around the cursor, which assumes the Lezer grammar is structured enough to provide that context.

**Net:** both APIs are mature and support the (a) static-now / (b) dynamic-later swap the task asks about — async completion sources are first-class on both. CodeMirror has a documented edge for the specific "swap in metadata-aware DB completions" use case because `@codemirror/lang-sql` already ships `schemaCompletionSource()`; Monaco has no equivalent built-in and the pattern (merge keywords + dynamic names, dispose-and-reregister on schema change) must be assembled by hand, though it is a well-documented, commonly-repeated pattern across multiple real projects (Superset, YDB's YQL editor). Confidence: **high** — both APIs and the `schemaCompletionSource` helper are confirmed from official docs/source and a maintainer forum post.

## 3. Built-in find/replace, multi-cursor, command palette, code folding, minimap

**Monaco** is the VS Code editor core extracted for the web, and ships these "assembled" with minimal setup: find/replace (regex + multi-cursor aware, triggered via an internal command, no separate package needed), multi-cursor editing, code folding, and a **minimap** — a feature CodeMirror has no built-in equivalent of. Monaco also carries VS Code's command-palette machinery as part of its IDE heritage.

**CodeMirror 6** ships a deliberately small core; `basicSetup` (the `codemirror` meta-package's convenience bundle, confirmed from its documented source) assembles: `lineNumbers()`, `highlightActiveLineGutter()`, `history()` (+ `historyKeymap`), `foldGutter()` (+ `foldKeymap`), `drawSelection()`, `dropCursor()`, multiple-selection support, `bracketMatching()`, `closeBrackets()`, `autocompletion()` (+ `completionKeymap`), `highlightSelectionMatches()`, and `searchKeymap` (wired to `@codemirror/search`'s default search/replace panel) — i.e., **multi-cursor, folding, and find/replace are present in `basicSetup` out of the box**, assembled from `@codemirror/commands`, `@codemirror/search`, `@codemirror/language`, and `@codemirror/autocomplete`. **No minimap** exists anywhere in the CodeMirror ecosystem's core packages (a community package, `@replit/codemirror-minimap`, exists but its maintenance status was not verified in this research). **No built-in command-palette UI** was found in `basicSetup` or the documented package list — `basicSetup` wires keymaps (`defaultKeymap`, `searchKeymap`, etc.), not a palette UI; one blog source claimed CodeMirror 6 "has... a command palette," but this could not be corroborated against the actual `basicSetup` source or official docs, so it is flagged **low confidence / likely incorrect** — a command-palette-style UI would need to be built or sourced from a community package.

**Net:** Monaco delivers minimap + command palette + fully-assembled find/replace/fold/multi-cursor with near-zero setup, matching its "VS Code in a browser" positioning. CodeMirror's `basicSetup` already covers find/replace, multi-cursor, and folding (contrary to a perception that *everything* must be hand-assembled), but minimap and command-palette are gaps with no built-in CodeMirror answer — those would be custom-built or go without. Confidence: **high** for Monaco's feature set and CodeMirror's `basicSetup` contents (confirmed from documented package source); **low** specifically on the command-palette claim for CodeMirror, flagged above.

## 4. Bundle size in an Electron context specifically

**Does Monaco's footprint matter against Chromium's baseline?** Multiple sources frame Electron's installed size as dominated by the bundled Chromium+Node runtime itself — commonly cited at roughly 85-120MB+ before any application code is added. Against that floor, Monaco's few-MB-to-low-tens-of-MB footprint is a secondary concern for *installer size*. One Electron maintainer-adjacent GitHub discussion makes the general point directly: "there is only so much you can take out of Chromium, Node.js, V8... and still have a working product." On that basis, the "Monaco's size is noise in Electron" framing is **plausible and consistent with available numbers**, though no source directly benchmarked a shipped Electron+Monaco app's installer size against an equivalent Electron+CodeMirror build to confirm the magnitude precisely — this is **medium confidence**, reasoned from component sizes rather than measured end-to-end.

**Important caveat on "Monaco is 5-6MB+":** the frequently-cited larger figures (one 2025 bundle report found a `ts.worker.js` of 6.68 MiB and an additional ~6.4 MiB chunk) are driven by Monaco's **TypeScript language service**, which a SQL-only query editor would never load — `MonacoEnvironment.getWorker` can be wired to return only the generic `editor.worker` and skip `ts.worker`/`html.worker`/etc. entirely. Citing "Monaco costs 5-6MB+" without that caveat overstates the footprint for this specific use case.

**Electron-specific integration friction — this is where the editors diverge, not raw size:**
- **Monaco requires web worker wiring**, and this is a documented, recurring source of Electron-specific bugs: a March 2025 GitHub issue showed Monaco's AMD loader (`@monaco-editor/loader` v4.7.0) failing specifically under Electron's `file://` protocol ("Didn't receive define call..."), which worked fine in the prior version — attributed to the AMD loader not handling Electron reading scripts via `file://`/Node's `fs` rather than over HTTP(S). The ecosystem's response has been migrating to Monaco's **ESM build** with explicit `MonacoEnvironment.getWorker` wiring (confirmed via a 2025 Wave Terminal Electron migration: drop the AMD loader, import `monaco-editor/esm/...` workers directly, set `base: './'` in the bundler for packaged `file://` loading, lazy-load the Monaco setup module). Additional documented gotchas: custom (non-built-in) languages' workers don't fire via `getWorker`/`getWorkerUrl` unless explicitly wired through bundler-plugin configuration (e.g., `monaco-editor-webpack-plugin`'s `customLanguages` option); ASAR packaging can bloat if source maps/`.ts` files/unminified Monaco code are shipped inside the archive (one case study, Arduino IDE, halved loaded-resource size — 21.2MB → 9.4MB — purely by switching to minified Monaco code).
- **CodeMirror needs no web workers at all** — it is a synchronous, in-process editor with no separate "language service" architecture the way Monaco (as a VS Code extraction) has. This means the entire class of problems above (AMD/ESM loader behavior under `file://`, worker-path resolution inside `asar`, per-language worker wiring) does not exist for CodeMirror in Electron. No source was found describing CodeMirror-specific Electron integration problems, which is itself consistent with it having a simpler, worker-free runtime model — but this is an absence of evidence, not a confirmed clean bill of health (medium confidence).

**Net:** bundle-size *in bytes* is plausibly noise against Electron's Chromium baseline (medium confidence, reasoned not directly benchmarked). The more concrete, better-evidenced Electron-specific difference is **architectural, not size-based** — but it is narrower than "Monaco manages a fleet of language-service workers": because QueryForge's Cosmos/T-SQL dialects are custom (non-built-in) languages, Monaco's `getWorker`/`getWorkerUrl` never fires for them, so the real surface is "wire one `editor.worker` correctly for packaged `file://`/asar loading," not the full TypeScript/JSON/CSS worker fleet. That smaller surface is still a real, recurring, documented category of Electron-specific bugs (AMD-vs-ESM loader behavior under `file://`, asar-packaged worker-script resolution) that CodeMirror's worker-free design avoids entirely, since it needs no web workers for any of its functionality.

## 5. Current maintenance status

**Monaco Editor (`microsoft/monaco-editor`) — actively maintained, high confidence (verified directly via npm).** Latest published version at time of this research: **0.57.0** (package's registry `modified` field reads 2026-09-24 — a package-level timestamp updated on any publish, not confirmed as the exact publish time of 0.57.0 specifically), with a visible, continuous version history through 2025-2026 including numerous dated nightly dev builds (e.g., `0.56.0-dev-20260204` through `-20260211`) and sequential stable releases (0.55.0 → 0.55.1 → 0.56.0 → 0.57.0-rc.2 → 0.57.0). This is a **correction of this research's own earlier web-search results**, which returned self-contradictory release counts and dates ("188 releases" vs "608 releases," "last release 4 months ago" on a date that doesn't reconcile) — those specific numbers should be disregarded in favor of the npm-registry-verified figures above. The underlying conclusion those searches pointed to (frequent Microsoft-driven releases, active issue triage into 2026) is corroborated by the verified version cadence and is **high confidence**.

**CodeMirror 6 — actively maintained, high confidence (corroborated by multiple independent signals).** `codemirror` meta-package and `@codemirror/lang-sql` are both current on npm (v6.10.0 / v6.x lines). `@uiw/react-codemirror`, the most common React wrapper, shows frequent recent releases (v4.25.12, npm `modified` timestamp 2026-09-24 — confirmed directly via npm). Maintainer Marijn Haverbeke's blog shows continued technical engagement into late 2025. Third-party adoption evidence (Wikimedia/MediaWiki actively extending CodeMirror 6 through 2026) further corroborates active use and maintenance. Funding model is sponsor-based (not a formal subscription), per CodeMirror's own site — a different risk profile from Microsoft-backed Monaco, but not itself evidence of reduced activity.

**One concrete staleness signal — but in a wrapper, not either core project.** `@monaco-editor/react` (the `suren-atoyan` npm package the task names as Monaco's React integration path) was **last published 2025-02-13** (confirmed directly via `npm view`) — roughly 20 months before this research's date (2026-10-07). This sits alongside open, unresolved issues as recent as 2026 (an "InstantiationService has been disposed" crash on React 18+ activity-reconnect cycles; a Safari-specific JS error reported Sept 2026) with no new release addressing them as of this research. This is a fact about the **wrapper package specifically** — Monaco core itself (the `monaco-editor` npm package) is, per above, actively released. Any Electron/React integration would need to independently evaluate whether to depend on this wrapper, maintain a fork, or integrate `monaco-editor` directly without it. Confidence: **high** for the publish-date fact (verified directly via `npm view`); **medium** for whether the open crash issues are still unresolved at the exact moment of implementation (issue trackers change).

**Net:** both core projects (Monaco, CodeMirror 6) show active, current, well-evidenced maintenance through 2026 — no credible sign of either slowing down was found. The one maintenance-risk signal found in this research is narrower and more specific than "Monaco vs. CodeMirror": it's the `@monaco-editor/react` wrapper's ~20-month release gap plus unresolved 2026-dated bug reports, a detail worth weighing if that specific wrapper (rather than `monaco-editor` directly, or an alternative wrapper) is the intended integration path.
