# Research: Entra ID Auth Flow & Credential Storage for an Electron Desktop App

## Summary

Microsoft's own recommended MSAL Node persistence plugin, `@azure/msal-node-extensions`, **still has a hard runtime dependency on `keytar`** (`keytar: ^7.8.0` in the latest published version, `5.5.2`, released 5 days before this research on the npm registry) — confirmed directly against the npm registry rather than secondary sources. `keytar`'s own last actual code release was **2022-02-17** (v7.9.0); its upstream repo (`atom/node-keytar`) is archived. A Microsoft-authored GitHub issue proposing migration off `keytar` to `@napi-rs/keyring` has been **open since June 2024 with zero maintainer response** as of Oct 2026 — it is an unconfirmed feature request, not planned work. This is a real, current-state risk exactly as the prior research flagged for Electron's general credential-storage story. Separately, `msal-node` itself exposes a documented, officially-sanctioned `ICachePlugin` interface (`beforeCacheAccess`/`afterCacheAccess`) that lets an app supply its own cache persistence — meaning QueryForge could serialize MSAL's cache and encrypt/store it via Electron's `safeStorage` directly, bypassing `msal-node-extensions` and its `keytar` dependency chain entirely, at the cost of losing that package's built-in cross-process file locking (and Windows/Linux-broker wiring, which QueryForge likely doesn't need). On flow choice: Microsoft's current guidance is unambiguous — interactive Authorization Code + PKCE via the system browser and a loopback (`http://localhost`) redirect is the recommended desktop pattern (`acquireTokenInteractive`), device code flow is a fallback for browser-less/input-constrained devices only (and is now flagged by Microsoft's own security guidance as high-phishing-risk, to be minimized rather than defaulted to), and ROPC is explicitly discouraged (no MFA/Conditional Access support, with an enforcement change landing March 27, 2026 that will break ROPC flows under Conditional Access). Embedded-webview OAuth remains discouraged industry-wide in 2025/2026 (Google now bans it outright for its own OAuth; Microsoft's own 2025 product direction is shifting federated sign-in to the system browser); `acquireTokenInteractive`'s loopback-server approach (opening the system browser, catching the redirect on a locally-bound HTTP server) is still the documented Electron pattern, not an embedded `BrowserWindow`. Once persisted, MSAL's cache supports fully automatic silent refresh via `acquireTokenSilent` across app restarts — no re-prompt needed as long as the underlying refresh token is still valid (desktop/native public-client refresh tokens get a 90-day sliding window that resets on each use within 24 hours, not the 24-hour hard cap that applies only to SPA-registered redirect URIs).

## 1. Does MSAL Node's official persistence plugin depend on keytar?

**Yes, confirmed directly against the npm registry (high confidence).** `npm view @azure/msal-node-extensions` on the latest published version (`5.5.2`, published ~5 days before this research) shows:

```
dependencies:
@azure/msal-common: 16.14.2
@azure/msal-node-runtime: ^0.20.0
keytar: ^7.8.0
```

`keytar`'s own registry history shows its **last actual version (7.9.0) was published 2022-02-17** — no new code release since, consistent with the prior research's finding that `atom/node-keytar` is archived/unmaintained since ~Dec 2022. (npm's package-level `modified` timestamp shows a later date, 2025-07-30, but this reflects registry metadata activity — e.g. maintainer list changes — not a new version; version `7.9.0` itself has no `deprecated` flag set and no newer version exists.)

This is not a hypothetical or edge-case dependency: multiple real-world issues confirm it causes active problems in 2025/2026 — `npm install` failures in network-restricted environments (`keytar` is a required, not optional, native dependency requiring a prebuild-CDN then node-gyp-headers fallback network path); missing prebuilt binaries for `win32-arm64`; and ESM-import incompatibility (the CJS-only `keytar` import breaks the `.mjs` build of `KeychainPersistence`).

**Microsoft has an open but unaccepted migration proposal, not a shipped fix.** [GitHub issue #7170](https://github.com/AzureAD/microsoft-authentication-library-for-js/issues/7170), opened by a Microsoft-affiliated contributor on **June 17, 2024**, proposes migrating to `@napi-rs/keyring` (a Rust-`keyring-rs`-backed napi-rs binding). As of this research the issue remains **open, unanswered by any MSAL.js maintainer, and labeled `feature-unconfirmed`** — no timeline, no linked PR, no milestone. Community workarounds exist only at the *consumer* level (e.g., a `beep-effect` PR making `msal-node-extensions` an optional peer dependency so `keytar` never enters the install graph for projects that don't need native persistence) — these don't change what the upstream package ships.

**Important nuance on where keytar is actually invoked:** on Windows, `msal-node-extensions`' persistence implementation (`FilePersistenceWithDataProtection`) uses DPAPI directly and **never calls into `keytar`'s native functions at all** — `keytar`'s native bindings are only actually exercised on macOS (Keychain) and Linux (libsecret). This means the Windows path is unaffected functionally by `keytar`'s unmaintained status (though the dependency is still present in the install graph and can break `npm install` regardless of target OS), while macOS/Linux persistence genuinely executes unmaintained native code at runtime.

## 2. Current Microsoft-recommended auth flow for a desktop app with GUI + browser access

**Confirmed current (high confidence), no material change found for 2025/2026 beyond tightening the ROPC/device-code cautions:**

- **Recommended: Interactive Authorization Code flow with PKCE**, via `msal-node`'s `PublicClientApplication.acquireTokenInteractive`. This is what Microsoft's own [Electron desktop quickstart](https://learn.microsoft.com/en-us/entra/identity-platform/quickstart-v2-nodejs-desktop) and the [desktop interactive-token-acquisition doc](https://learn.microsoft.com/en-us/entra/identity-platform/scenario-desktop-acquire-token-interactive) use. PKCE is handled automatically by MSAL (code verifier/challenge generated internally).
- **Fallback only: Device code flow** — Microsoft's docs frame it as for devices "without access to a web browser." Microsoft's own 2025/2026 security guidance (Entra blog, techcommunity post) now explicitly discourages using it as a general-purpose pattern even where it technically works, because it has been weaponized for phishing (attacker-initiated device-code prompts relayed to victims via legitimate client apps like Azure CLI/Graph PowerShell/Teams). Guidance: "get as close as possible to a unilateral block on Device Code Flow, allowing it only in well-documented and secured use cases." Not relevant for QueryForge, which has full GUI + browser access.
- **Explicitly discouraged: ROPC (Resource Owner Password Credentials)** — "no longer recommended" per Microsoft's own MSAL docs; no MFA, no Conditional Access, no SSO support; works only for work/school accounts. A **dated enforcement change (MC1223829), effective March 27, 2026**, will cause ROPC flows relying on Conditional Access resource exclusions to start failing — i.e., this is becoming actively more broken, not just discouraged, within QueryForge's likely build window.
- **Nothing found indicating a 2025/2026 change to this hierarchy** beyond the increased explicitness of the device-code-flow phishing warnings and the March 2026 ROPC/Conditional-Access enforcement date — the underlying recommendation (interactive PKCE for GUI apps) is unchanged and longstanding.

## 3. Does msal-node need msal-node-extensions, or can QueryForge self-serialize via safeStorage?

**`msal-node` does not require `msal-node-extensions` to function — cache persistence is an explicit, documented extension point.** `msal-node`'s `PublicClientApplication`/`ClientApplication` accepts an `ICachePlugin` in its configuration:

```ts
interface ICachePlugin {
    beforeCacheAccess: (tokenCacheContext: TokenCacheContext) => Promise<void>;
    afterCacheAccess: (tokenCacheContext: TokenCacheContext) => Promise<void>;
}
```

MSAL fires these hooks around in-memory cache access; a plugin loads serialized cache data before access and, if `cacheContext.cacheHasChanged`, persists `cacheContext.tokenCache.serialize()` afterward. Microsoft's own configuration docs show this with a plain JSON file; the same shape drops in cleanly with Electron's `safeStorage.encryptString()`/`decryptString()` substituted for plaintext file I/O — i.e., exactly the pattern the prior research (01-desktop-framework.md §2) already established QueryForge would need to build for its other secrets (SQL credentials, Cosmos keys). This would avoid pulling in `@azure/msal-node-extensions` (and therefore `keytar`) entirely.

**What QueryForge would lose by doing this (what `msal-node-extensions`'s `PersistenceCachePlugin` provides beyond encrypt-and-persist):**
- **Cross-process file locking.** `PersistenceCachePlugin` (via its internal `CrossPlatformLock`) creates a lock file tied to the cache file path and holds it between `beforeCacheAccess` and `afterCacheAccess`, so multiple OS processes sharing the same cache file don't race/corrupt it. This matters if QueryForge could ever run multiple instances/windows as separate OS processes touching the same persisted MSAL cache concurrently — the locking mechanism itself has known rough edges in practice (reported `CrossPlatformLockError` lock-acquisition failures and `EPERM` lockfile-unlink races under high concurrency), so it is not purely an upside even if you take the dependency.
- **`Environment` helper utilities** for cross-platform default cache-path construction (minor convenience, trivially replicable).
- **Native broker interop** (via the separate `@azure/msal-node-runtime` native addon dependency) for Windows Web Account Manager/SSO-with-other-native-apps — out of scope unless QueryForge wants OS-broker-level SSO, which is a separate, optional feature from plain cache persistence.

A self-rolled `safeStorage`-backed `ICachePlugin` would need to hand-implement at minimum basic single-process safety (QueryForge is a single Electron app, not obviously multi-process against the same cache file, so the cross-process locking gap may not matter) and would fully sidestep the `keytar` dependency-chain risk from §1.

## 4. Token refresh / long-lived sessions & loopback-redirect gotchas

**Silent refresh across launches: yes, automatic, by design — contingent on cache persistence being wired correctly.** `acquireTokenSilent` looks up the cached account/token; if the access token is expired but a valid refresh token exists, MSAL exchanges it silently with no user interaction. Refresh tokens are never exposed to app code (accessible only internally via the cache). This works across process restarts as long as (a) a cache plugin persists the serialized cache to disk/secure-storage and (b) that same persisted cache + the stored `AccountInfo` object are reloaded and passed to `acquireTokenSilent` on the next launch. A real documented gotcha: at least one GitHub issue reports cache-plugin hooks silently not being invoked for `acquireTokenSilent` under certain wiring, falling back to in-memory cache and throwing `no_tokens_found` — this means the plugin wiring needs explicit verification/testing, not just a line of config, before relying on "silent refresh across launches" as guaranteed behavior.

**Refresh token lifetime:** For a genuine native/public-client desktop app registration (not a `spa`-type redirect URI), the refresh token gets a **90-day rolling/sliding window that resets on each use, with a ~24-hour inactivity cutoff** (if unused for >24h, e.g. the user's machine is off for a day+, it expires and forces re-auth) — not the hard 24-hour cap that applies specifically to SPA-registered redirect URIs. Getting the app registration's redirect-URI platform type wrong (registering as `spa` instead of the desktop/"Mobile and desktop applications" platform) is a documented, easy-to-hit mistake that silently locks the app into the much shorter SPA refresh-token lifetime.

**Loopback-redirect mechanics and gotchas (Electron-specific):**
- Microsoft's official Electron quickstart and `acquireTokenInteractive` spin up a **temporary local HTTP server bound to loopback (`http://localhost`)** to catch the authorization-code redirect, then opens the **system default browser** (via `shell.openExternal` in the Electron sample) for the actual sign-in — not an embedded `BrowserWindow`.
- **Port conflicts/dynamic port selection:** real-world Electron implementations bind to `127.0.0.1` (not `0.0.0.0`) and should not hard-assume a fixed port is free; dynamic/ephemeral port selection with collision handling is the documented best practice, since a fixed default port can collide with other local services.
- **`shell.openExternal` carries its own security risk if misused.** Electron's own security docs warn that `shell.openExternal` can be leveraged for remote code execution if passed untrusted/unvalidated URIs (a real CVE-level incident occurred in Wire Desktop from exactly this misuse-pattern, fixed via protocol/URL allowlisting before calling `openExternal`). Relevant to QueryForge only insofar as the URL passed to `openExternal` for the auth flow must be the known, fixed Entra authorize-endpoint URL under app control, not externally influenced input.
- **Embedded `BrowserWindow`-based OAuth remains discouraged, and the industry trend has hardened against it since 2024, not relaxed.** Google now outright bans Google OAuth inside embedded webviews. Microsoft's own 2025 product direction (Oct 2025 Entra blog) is moving federated-IdP sign-in *away* from embedded webviews toward the system browser specifically to support WebAuthn/passkey flows that many embedded webviews can't handle, and some IdPs now refuse to serve login pages to embedded views at all. MSAL.NET still technically supports an embedded-webview option but requires it be explicitly, separately opted into (`Microsoft.Identity.Client.Desktop` + `.WithWindowsEmbeddedBrowserSupport()`) rather than being the default — a deliberate friction point, not an endorsement. No evidence found of this guidance relaxing in 2025/2026; if anything it has gotten stricter.
