# Research: Desktop Framework Compatibility (Electron vs Tauri)

## Summary

Electron's main process is plain Node.js, so `@azure/cosmos`, `mssql`/`tedious` are pure-JS packages with no native bindings — they run there with no ABI or binding story at all. Tauri's Rust core cannot run these Node SDKs directly; QueryForge would need to pick between (a) official-but-pre-1.0 Rust Azure SDKs plus an unmaintained-upstream SQL Server driver, or (b) bundling a Node sidecar, which claws back most of Tauri's size/memory advantage and reintroduces packaging complexity (the tool Tauri's own docs recommend for this, `pkg`, was deprecated in Jan 2024). Secrets storage is mature on both sides but shaped differently: Electron's `safeStorage` is a blob encrypt/decrypt primitive (app persists ciphertext itself), while Tauri's ecosystem is converging on the actively-maintained Rust `keyring` crate, which gives native named-entry OS-store semantics directly. Packaging/signing requirements (Apple notarization, Windows Authenticode-on-HSM) are identical regardless of tool, and both electron-builder and Tauri's bundler now handle universal (Apple Silicon + Intel) macOS builds via `lipo`. Bundle-size/memory numbers favor Tauri in most sources but by a smaller margin in the one more rigorous independent benchmark found, and that same benchmark found Electron *faster* at cold start — the marketed numbers and measured numbers disagree on this axis.

## 1. Database SDK compatibility

**Electron — confirmed, high confidence.** Electron's main process is a full Node.js environment. `@azure/cosmos`, `mssql`, and `tedious` are pure JavaScript/TypeScript packages with no native (C/C++ or Rust) bindings in their default configuration — the one native-code option in this space, `msnodesqlv8` (an alternative SQL Server driver using the Microsoft ODBC driver), is optional and Windows-only, and isn't required for `mssql`/`tedious` to work. Because there's no native module in the dependency chain, there is no ABI/rebuild story to manage (contrast with `better-sqlite3`, below) — these packages install and run in the main process like any other npm package would under Node.

**Tauri — no Node runtime in-process; two real paths, neither as simple as Electron's.** Tauri's core is Rust compiled to a native binary; there is no JS engine capable of running Node-targeted code inside it, only the OS webview's browser JS engine (which has no `require`/Node APIs). Two options exist:

- **Option A: Rust-native database clients.**
  - **Cosmos DB**: Microsoft publishes an official `azure_data_cosmos` crate (public preview announced Feb 26, 2025). As of this research (Oct 2026) it has progressed through rapid 0.x releases (e.g., 0.37.1 in Jul 2026, 0.38.0 in Sep 2026) to a `1.0.0-beta.1` pre-release (Sep 29, 2026) — i.e., it is still pre-1.0/beta, not yet GA-stable. It supports Entra ID and key-based auth, CRUD, and querying via `CosmosClient`/`PartitionKey`/`Query`. We could not confirm from documentation whether its query surface fully covers what a schema/query-browser tool needs (cross-partition query execution, continuation-token paging, per-request RU-charge reporting, container/index-policy enumeration for a schema tree) — this needs direct hands-on verification against the crate's current API, not just docs skimming. Microsoft explicitly warns to use only the official `azure_data_cosmos` crate, not community crates named `azure_cosmos`/`azure_sdk_for_rust`.
  - **Azure SQL**: The de facto native Rust TDS driver, `tiberius`, is reported (early-2025 Rust forum post) as "effectively unmaintained," with unanswered issues/PRs and open, unpatched RustSec advisories in its TLS path (rustls/webpki certificate verification). The community has responded with forks: `tiberius-ng` (full-history continuation, same license) and a Keeper-Security fork. Microsoft has also started its own effort (`mssql-tds-preview` / `mssql-tiberius-bridge`), described as a "publishable fork... until the official crate lands on crates.io" — i.e., not yet an official, released Microsoft SDK. **Bottom line: a mature, actively-maintained, officially-backed Rust Azure SQL client does not yet exist (as of Oct 2026); the ecosystem is mid-transition.**
  - Cost of Option A: QueryForge's entire database access layer would need to be written and maintained in Rust against pre-1.0/transitional crates, rather than reusing the official, GA, widely-used JS SDKs.

- **Option B: Node.js sidecar process.** Tauri officially documents this pattern: compile a Node.js backend to a standalone binary, place it in `src-tauri/binaries/<name>-<target-triple>`, declare it in `tauri.conf.json`'s `bundle.externalBin`, and invoke it via `@tauri-apps/plugin-shell`'s `Command.sidecar(...)` over IPC (not literally "inside" Tauri — it's a separately-spawned OS process). This lets `@azure/cosmos`/`mssql` run unmodified in the sidecar. Two costs:
  - Tauri's own docs recommend compiling the sidecar with `pkg` — but `vercel/pkg` was **archived/deprecated in Jan 2024** (final release 5.8.1), with an unpatched CVE (CVE-2024-24828, predictable temp-file paths). The community fork `@yao-pkg/pkg` is the maintained drop-in replacement; Node's own built-in Single Executable Application (SEA) support (stable since Node 19.7/18.16, improved further through Node 25) is the other alternative, but `pkg`-style and SEA binaries are built **per architecture/target-triple**, not universal — relevant for the "Apple Silicon + Intel" requirement (see §4).
  - A bundled Node runtime inside the sidecar is reported to typically add on the order of tens of MB (community estimates cited in the ~40-80MB range) back onto the install size, eroding much of Tauri's headline bundle-size advantage (see §5) for this specific app.

**Conditional framing:** if Tauri is chosen, QueryForge's DB layer is either (a) built against pre-1.0/transitional Rust crates with an unresolved maintenance gap on the SQL Server side, or (b) a Node sidecar that restores JS SDK compatibility at the cost of bundle size and an extra per-arch packaging step. Electron avoids this decision entirely.

## 2. OS credential store integration

**Electron:**
- `keytar` (native Node module wrapping macOS Keychain / Windows Credential Manager / libsecret) is **archived/unmaintained** — upstream (`atom/node-keytar`) has had no activity since ~Dec 2022; Snyk Advisor lists it as "ARCHIVED." Multiple major Electron apps (VS Code, Element Desktop, Joplin, Checker Network/Filecoin Station) have documented migrating off it during 2024.
- The replacement is Electron's built-in `safeStorage` API. **Important distinction (not purely a name swap):** `safeStorage` is an **encrypt/decrypt-blob primitive**, not a named-credential store. On macOS it uses a single app-level encryption key held in Keychain; on Windows it uses DPAPI. The application is still responsible for persisting the resulting ciphertext (e.g., to a local file or its own SQLite DB) and for its own key→value/connection-name mapping. For a tool like QueryForge that needs to store **N named connection credentials**, this is a different shape of integration work than keytar's (or Tauri's) named-entry keychain API — expect to build a thin storage layer on top of `safeStorage`, not get one for free.

**Tauri:**
- The official `tauri-plugin-stronghold` (IOTA Stronghold-based) is explicitly being phased out: Tauri maintainers have stated Stronghold "is no longer recommended and will be deprecated and therefore removed in v3," largely because it requires a user-managed password/vault rather than tapping the native OS store.
- The ecosystem is converging on wrappers around the Rust **`keyring` crate**, which directly targets macOS Keychain, Windows Credential Manager, and Linux Secret Service with named-entry semantics (closer to what keytar offered). The `keyring` crate itself is **actively maintained** (current maintainer Dan Brotsky; frequent releases through mid-2026; 100/100 maintenance score on Socket.dev; ~2.6M downloads/month; recently refactored into `keyring-core` + per-platform store crates such as `windows-native-keyring-store`, `apple-native-keyring-store`).
- Several thin Tauri plugins wrap this crate: `tauri-plugin-keyring` (at least two independently maintained projects by that name — HuakunShen's and charlesportwoodii's), `tauri-plugin-secure-keystore`, and `tauri-plugin-keyring-store` (a Stronghold-API-shaped wrapper). These plugins are newer and smaller than the underlying `keyring` crate itself; their own maintenance history is shorter and should be evaluated independently of the crate's maturity.

**Net:** both platforms have a credible, maintained path to native OS credential stores, but the *shape* differs — Electron's official path (`safeStorage`) requires the app to build its own named-credential layer on top of a blob API, while Tauri's community path (`keyring`-backed plugins) more directly models named credentials, riding on a well-maintained underlying crate but thinner/newer plugin wrappers.

## 3. Embedded SQLite

**Electron — `better-sqlite3`:** Widely used, synchronous, well-regarded API. As of v13 it moved to **Node-API (N-API)**, which provides ABI stability across Node/Electron versions in principle (one prebuild per OS/CPU rather than per-Electron-version). This is a real maturity improvement, but real-world ABI mismatches are still reported in 2025-2026 (e.g., `ERR_DLOPEN_FAILED` when a locally-built addon's Node ABI version doesn't match the Electron runtime's expected ABI) — maintainers and the community attribute these to project/build tooling rather than defects in the library, and the standard mitigation (`electron-rebuild`, rebuilding on `postinstall`) is well established. Electron version bumps still require native modules to move in lockstep (e.g., C++20 requirements starting at Electron 33). Major Electron apps (VS Code, Signal, Joplin, Actual) all ship `better-sqlite3` successfully today.

**Tauri — `tauri-plugin-sql` / `rusqlite`:** The **official** `tauri-plugin-sql` plugin is sqlx-based (not rusqlite), actively maintained by the core Tauri org (92 contributors), with regular 2025-2026 releases, and supports sqlite/mysql/postgres plus mobile (iOS/Android). There is **no official rusqlite-backed plugin**; community forks exist (`tauri-plugin-rusqlite2`, actively released through early 2026, adds transactions/migrations/SQLCipher but explicitly untested on mobile; `@bspeckco/tauri-plugin-sqlite`, less active; `tauri-plugin-rusqlite`, stale, still Tauri v1-only). The underlying `rusqlite` crate itself is a long-standing, mature, widely-used Rust SQLite binding independent of any Tauri plugin. For a desktop-only app like QueryForge, using `rusqlite` directly from Rust application code (bypassing a Tauri SQL plugin entirely) is also a viable, arguably simpler option, since there's no need for the plugin's JS-invoke bridge if the query/caching logic lives natively in Rust.

**Net:** both ecosystems have mature underlying SQLite bindings (`better-sqlite3`'s N-API build, `rusqlite`). Electron's ABI/native-module coupling is a known, manageable but recurring source of friction across Electron upgrades; Tauri sidesteps this (Rust crates compile against the app's own Rust toolchain, no separate "runtime ABI" to track), but the *official* Tauri SQL plugin is sqlx/async-based rather than rusqlite, and the rusqlite-specific plugin path is community-maintained only.

## 4. Packaging/installer maturity for macOS + Windows

**Underlying OS requirements are identical regardless of tool.** Both platforms need: macOS — a paid Apple Developer Program Developer ID Application certificate, code signing with Hardened Runtime enabled, then notarization via Apple's `notarytool` (replacing the deprecated `altool`, discontinued Nov 2023), plus ticket stapling. Windows — an OV/EV Authenticode certificate whose private key must live on certified hardware (token/HSM/cloud signing service) since June 1, 2023 (plain `.pfx` file signing is no longer issuable for new certs). Unsigned apps face Gatekeeper blocking on macOS and SmartScreen "unknown publisher" warnings on Windows either way.

**Electron:** Two community tools dominate — **electron-builder** (broadest format support: NSIS, MSI, DMG, PKG, MAS, AppX, deb, rpm, Snap, AppImage; built-in `electron-updater` auto-update integration; config-driven signing via `mac.notarize`, `win.sign`/`win.signtoolOptions`/`win.azureSignOptions`) and **Electron Forge** (the Electron-project-official scaffolding+build tool, requiring more manual orchestration of the same underlying `@electron/notarize`/signing calls). Both are long-established with large install bases and extensive community documentation; electron-builder is generally regarded as the more full-featured/batteries-included option for signing and multi-format output. A hard Squirrel.Mac constraint: macOS auto-update requires the app to be signed — there's no unsigned-but-silently-self-updating path.

**Tauri:** Signing/notarization/bundling is built directly into the **Rust-native Tauri bundler** itself (not a separate community tool), triggered by `APPLE_*` env vars (macOS) or `bundle.windows.signCommand` (Windows). This has matured substantially: v1.5 added signing of sidecars/frameworks/NSIS uninstallers; the switch to `notarytool` (over deprecated `altool`) is done; 2025 added developer-experience flags (`--skip-stapling`, Aug 2025; `--no-sign`, Oct 2025); NSIS itself was updated 3.8→3.11 in late 2025; WiX (MSI) and NSIS DLL signing coverage expanded through v2.4–2.5.2 (mid-2025). Overall trajectory is "basic signing support in 2023 → fairly comprehensive by late 2025/2026," but the community/ecosystem (StackOverflow answers, blog posts, third-party troubleshooting content) is smaller than Electron's given Tauri's shorter history and smaller install base.

**Universal (Apple Silicon + Intel) macOS builds — relevant given QueryForge's explicit target:**
- electron-builder: native support via `mac.target: universal` (or `--universal` CLI flag); downloads both x64 and arm64 Electron runtime builds and merges them with `lipo`; for native modules it needs explicit handling (`mergeASARs`, `singleArchFiles` for `.node` files) since two separate ASAR archives (one per arch) must be reconciled.
- Tauri: `cargo tauri build --target universal-apple-darwin` (after `rustup target add x86_64-apple-darwin aarch64-apple-darwin`) compiles the Rust core twice and `lipo`-merges, in one command. **Caveat relevant to §1's sidecar option**: if a Node sidecar is used, the sidecar binary itself must separately be built per-architecture (or as its own universal binary) and selected at runtime — Tauri's docs advise checking whether the sidecar vendor/tool can produce a universal binary, or bundling both arch variants and choosing by `std::env::consts::ARCH`. Since `pkg`/SEA-based Node binaries are produced per-target, this is extra manual work not needed on the Electron side (where the Node runtime is Electron's own, already merged by electron-builder).

**Net:** both tools reach the same OS-mandated destination; electron-builder's community tooling and track record are larger/longer-standing, while Tauri's bundler is natively integrated (one tool, not a separate packager) and has closed most of its gaps by 2025-2026 — but the universal-build story gets materially more complex on Tauri if a Node sidecar is in play.

## 5. Bundle size / startup time / memory footprint

Numbers vary significantly by source, and the gap between **marketing-style comparisons** and the **one more rigorous, methodology-disclosed benchmark found (Betterstack)** is itself a finding:

| Metric | Marketing/blog consensus (multiple 2025-2026 sources) | Betterstack (stated as testing equivalent real apps) |
|---|---|---|
| Bundle size | Electron ~120-323MB vs Tauri ~3-57MB (cited ratios from "20-50x" down to ~5-6x) | Electron 323MB vs Tauri 57MB |
| Idle memory | Electron ~150-400MB vs Tauri ~20-80MB (~5x) | (consistent with lower end of above range) |
| Cold start | Tauri "~200ms-380ms" vs Electron "~1.4-5s" (most blogs) | **Electron 273ms vs Tauri 311ms — Electron measured faster** |

The stated mechanism for the startup reversal: Tauri's Rust backend itself starts fast, but the app still waits on the **OS webview's own initialization** (WebView2 on Windows in particular is called out as having first-launch overhead); Electron ships a pre-initialized, bundled Chromium that doesn't pay that separate "cold OS component" tax. We flag this as **low-to-medium confidence** either way — one benchmark contradicting a large volume of marketing claims doesn't settle it, but it's a real, mechanistically-plausible counter-data-point that a human evaluator should weight against vendor-style blog comparisons.

**Size/memory advantage is conditional on §1's answer:** the commonly-cited 3-10MB-ish Tauri bundle figures assume a pure Rust+webview app. If QueryForge on Tauri ships a bundled Node sidecar to get `@azure/cosmos`/`mssql` support, community estimates put the added footprint at roughly **+40-80MB** for the embedded Node runtime — which would close most or all of the headline size/memory gap with Electron for this specific app. We did not find a benchmark of a real Tauri+Node-sidecar app's installed size/memory to confirm this estimate precisely; treat it as directionally credible but unverified.

## 6. Other considerations

- **Background/worker query execution (long-running DB queries without freezing the UI):**
  - Electron: official guidance is to never block the main/UI process; use `worker_threads` for same-process concurrency, or the `utilityProcess` API (Electron's modern replacement for raw `child_process.fork`, Node-environment, can hold a `MessagePort` channel directly to a renderer) for stronger isolation/crash containment at the cost of extra memory/startup overhead per spawned process. Both are mature, documented patterns; community reports from 2025 do note occasional stability issues under sustained heavy `worker_threads` use (crashes after extended runs in at least one reported case), suggesting this needs real load-testing for a query tool that may run many long queries over a session.
  - Tauri: long-running DB work would run natively in Rust async tasks (tokio) in the backend process — no separate "worker" abstraction needed the way Electron needs one, since Rust async/threads don't block a shared JS event loop the way Node's main thread does. If a Node sidecar is used instead, the sidecar is already a separate OS process, so the isolation Electron gets from `utilityProcess` comes "for free" there, but at the sidecar-size cost noted above.
- **Multi-window support:** Tauri v2 added multi-webview/multi-window support, but as of the 2.0 release it's explicitly flagged by Tauri itself as **experimental/unstable** (behind a feature flag; `tauri::Window` was split into `tauri::WebviewWindow` as part of this transition). Electron's multi-`BrowserWindow` support is long-standing and fully stable/production-proven (it's one of Electron's oldest, most heavily used capabilities). For a DataGrip-style tool where multiple query/connection windows are a plausible core feature, this is a material maturity gap in Electron's favor, as of this research.
- **Auto-update:** Electron has mature, battle-tested options (`electron-updater` tied to electron-builder, Squirrel.Mac/Squirrel.Windows underpinnings) used by large production apps for years. Tauri's `tauri-plugin-updater` (v2.x) is actively developed (frequent releases) and functionally reasonably complete (static-JSON or dynamic update-server modes), but Tauri's own team cautions that official plugins don't necessarily share Tauri core's stability guarantees, and real-world adopters report needing to hand-wire plugin registration, `tauri.conf.json` config, capability permissions, and CI signing/upload — i.e., less "batteries-included" than Electron's auto-update story today.
- **Cross-engine rendering consistency (relevant to a data-grid-heavy UI):** Electron bundles one Chromium build, so rendering is consistent across all platforms by construction. Tauri renders via each OS's native webview (WKWebView/macOS, WebView2/Windows, WebKitGTK/Linux — the last not relevant to QueryForge's two target OSes), via the `wry` abstraction layer. This means CSS/layout can differ subtly between macOS and Windows builds and must be tested on both; cited as a real dealbreaker for at least one canvas-heavy app (Figma, per secondary sources) that couldn't rely on Tauri for this reason. For a tabular/grid-heavy query tool using standard DOM/CSS (tables, forms, modals) rather than custom canvas rendering, multiple sources describe this as "manageable with testing," not a likely blocker — but it is a real difference in guarantee between the two frameworks, and Windows additionally carries a WebView2-runtime-presence question (bundled vs. must-be-preinstalled) that needs to be nailed down explicitly for a Windows installer, whereas WKWebView is simply part of the macOS OS.
- **Credible third contender — Wails (Go):** Surfaced repeatedly in 2025-2026 comparison sources as a legitimate alternative, pairing a Go backend with the native OS webview (same "don't ship Chromium" architecture as Tauri) and auto-generating JS bindings from Go method signatures (no JSON-IPC bridge). Go has its own official Azure SDKs (Cosmos DB and SQL Server/`go-mssqldb` both exist) *(asserted from general knowledge, not verified in this research — the claim that Go's Azure SDK clients are comparatively more mature/stable than the Rust equivalents should be checked before it influences a decision; we did not search this directly)* — so Wails would plausibly avoid Tauri's Rust-crate-maturity problem from §1, at the cost of introducing a **third language/ecosystem** (Go) in addition to whatever the frontend uses, with no existing QueryForge code in Go. Wails has the smallest community/ecosystem of the three (~35K GitHub stars cited vs. Tauri/Electron's larger bases), and its headline performance numbers (~15MB bundle, ~10MB RAM, sub-0.5s start) are vendor/docs-reported and flagged by third-party sources as needing independent verification; more conservative third-party estimates cite 8-20MB installers and 80-150MB RAM. We include it here because it is a genuinely discussed contender for exactly this kind of app (Go backend + native webview + DB tooling), not because evidence points to it being the right choice.
