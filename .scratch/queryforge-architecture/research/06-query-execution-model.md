# Research: Query Execution Model (Electron Process/Thread Placement)

## Summary

Electron's main and renderer processes are confirmed-separate OS processes (Electron's own process-model docs state this explicitly), but they are not symmetric: the main process is Electron's single "control tower" — OS input events, window/GPU coordination, and all IPC for every window route through it — so Electron's own performance docs state in its own words that blocking the main process "means your entire app will freeze until the main process is ready to continue processing," not just that IPC gets delayed. Running `@azure/cosmos`/`mssql` queries themselves (pure async network I/O) in main does not block anything, matching the premise in the question. The real risk is CPU-bound work that happens to sit next to the query — chiefly `JSON.stringify`/`JSON.parse` and IPC/structured-clone serialization of large result sets — and that risk exists at two separate points: in main (delays all windows' IPC and OS-level responsiveness) and, independently, in the renderer receiving the payload (freezes that window's own paint/input — one source states main-process isolation does not fix this second point, since it is a renderer-side deserialization cost). Security guidance is unambiguous and unchanged for 2025/2026: `contextIsolation: true` + `nodeIntegration: false` + `contextBridge`, DB SDKs never in a renderer. On isolation mechanics: `worker_threads` share main's OS process and fault domain (a native-level crash/abort in a worker has been repeatedly reported, including a 2025 Electron regression, to take the whole app down), while `utilityProcess` is a true separate OS process via Chromium's Services API, explicitly positioned by Electron for "crash prone components," at the cost of per-instance Node-runtime memory/startup overhead and an app-ready lifecycle constraint. Cosmos and mssql cancellation are both SDK/driver-level (`AbortSignal` / `request.cancel()`) and neither requires process-level kill to work; the two differ in what cancellation actually does server-side, and mssql's connection pooling model has a concrete, process/thread-architecture-relevant cost under per-tab isolation.

## 1. Is this even a real problem?

**Confirmed, high confidence: async DB I/O itself does not block anything, in any location.** `@azure/cosmos` and `mssql`/`tedious` issue HTTP/TCP requests that libuv services without occupying the JS thread while waiting; this holds whether the SDK runs in Electron's main process or a worker/utility process. This part of the question's premise is correct and not in dispute in any source found.

**Confirmed, high confidence: Electron's main process is not a peer of the renderer it hosts — it is privileged, and blocking it is documented by Electron itself as an app-wide freeze, not merely an IPC delay.** Electron's official process-model docs (`electronjs.org/docs/latest/tutorial/process-model`, fetched directly) confirm main and each `BrowserWindow`'s renderer are separate processes, modeled on Chromium's own multi-process browser/renderer split. Electron's official performance docs (`electronjs.org/docs/latest/tutorial/performance`, fetched directly) state, in the document's own words: *"Under no circumstances should you block this process and the UI thread with long-running operations. Blocking the UI thread means that your entire app will freeze until the main process is ready to continue processing."* The document frames this as the main process acting as a control tower that routes OS input events and GPU/animation coordination, not merely an IPC endpoint — i.e., Electron's own docs claim the blast radius is broader than "IPC responses get delayed."

**One older, frequently-surfaced claim should be discounted.** Search results repeatedly surfaced a 2015-era Electron GitHub issue (#3363) containing the claim that main and renderer are "one process... gluing the two event loops together so they run alternately." This describes an architecture that predates Electron's move to Chromium's modern multi-process model and **contradicts** both the question's own correct premise and Electron's current process-model docs (fetched above), which describe genuinely separate OS processes. **Low confidence / discount this specific claim** — it should not be read as current.

**What should be believed instead — decomposed by effect, since "freezes the UI" bundles at least four distinct things with different evidentiary support:**

1. **Renderer paint/compositing.** Not confirmed independently blocked by main-process CPU work in the primary sources fetched (Electron's own docs don't address this directly). A 2017 community-reported issue (electron/electron#9719, "short blocking operations in main process freeze CSS animations in all renderer processes") claims this effect but is old and unverified against current Electron's compositor architecture (which runs via a separate GPU/Viz process in modern Chromium) — **low-to-medium confidence, dated**.
2. **Input event dispatch.** Electron's performance docs' own framing (input events route through main as "control tower") implies this is plausible and current, but no source found gives a precise current mechanism description. **Medium confidence.**
3. **IPC responses (`invoke`/`handle` and events) stalling for all windows while main's event loop is busy.** This is the best-supported, least-disputed effect: multiple independent community reports (GitHub issues #3363's practical reproduction, electron/electron#8244, the Actual Budget engineering writeup) converge on it, and it follows directly and uncontroversially from Node's single-threaded event-loop model applied to main. **High confidence.** This is also the one most directly relevant to QueryForge's multi-tab requirement (§4 below): if one tab's query-result processing occupies main's event loop with synchronous CPU work, every other tab's pending IPC (status updates, cancel requests, other query results) queues behind it.
4. **OS-level "app not responding" (macOS beachball / Windows ghosting).** Tied to main failing to pump its message loop; Sentry ships an "Event Loop Block"/ANR detector for Electron specifically because this is a known, monitorable failure mode. **Medium-to-high confidence** this is a real, current phenomenon, though exact OS-level mechanics weren't independently verified beyond Sentry's product description.

**The realistic failure mode for QueryForge specifically, synthesized from the above:** not the query execution itself, but **CPU-bound JSON work on a large result set**, in two places:
- **In main**, if query results are serialized (`JSON.stringify`) or otherwise processed synchronously in main before being sent over IPC — this is O(n) synchronous work that, per community benchmarks found, can cost tens to ~100ms+ for multi-MB payloads, during which main cannot service IPC for *any* window (point 3 above), and plausibly cannot service input/OS message-pump duties either (points 2/4).
- **Independently, in the renderer**, when that same large JSON payload arrives via IPC/`postMessage` and must be deserialized (structured-clone cost) and then re-rendered into a grid. One source found a concrete estimate: "if that payload is 10MB of JSON, V8 might take 50-100ms just to parse and GC the object" — and during that window, *that renderer's own* paint is blocked, regardless of how the query was executed or where. **This is a distinct failure mode from "main process blocking," and the same source states it is not solved by main-process worker/process isolation** — that source's own recommendation is to use pagination, streaming, or transferable/typed-array payloads instead of large plain-JSON IPC messages. Medium confidence on the specific millisecond figures (single blog-level source), high confidence on the mechanism (structured-clone/JSON parse being synchronous and O(n) is not disputed).

## 2. Security best practice (contextIsolation / nodeIntegration / contextBridge)

**Confirmed current, high confidence.** Electron's own security docs (fetched directly) state: *"Context Isolation is the default behavior in Electron since 12.0.0"* and, separately, *"[process sandboxing] is the default behavior in Electron since 20.0.0"* — these are two distinct settings that both default on today, not one setting with two version claims. `nodeIntegration: false` has been default since Electron 5 (per search-surfaced secondary sources). `contextBridge` remains the sanctioned mechanism for a preload script to expose a minimal, specific API surface to the renderer rather than passing `ipcRenderer` or Node built-ins through directly. A commonly recommended fuller baseline also adds `webSecurity: true`, `nodeIntegrationInWorker: false`, and `allowRunningInsecureContent: false`. Electron's own docs and third-party security writeups analyzing historical Discord/Element RCEs describe explicitly *disabling* `contextIsolation` (overriding the current default) as reopening the exact renderer-to-Node escalation path these settings exist to close — this is a statement about what happens if a developer turns the default off, not evidence against the default itself.

**Confirmed, high confidence: DB SDKs should not run in a renderer regardless of the main/worker/utilityProcess question.** This follows directly from (and is not in tension with) point 1 above — it is a separate concern (trust boundary / attack surface), not a performance one. A renderer that could `require('@azure/cosmos')` or `require('mssql')` directly would need `nodeIntegration: true`, which Electron's own docs state **also disables renderer sandboxing** for that window, i.e., accepting this is a categorical security regression independent of any UI-freeze concern. This holds equally whether the actual query execution later happens in main, a `worker_thread`, or a `utilityProcess` — in all three cases the SDK call is proxied from the renderer via `contextBridge`-exposed IPC methods, never invoked directly from renderer JS. One important nuance: even a textbook-correct `contextIsolation`/`sandbox` config does not protect against engine-level (V8/Chromium) vulnerabilities if Electron itself is not kept current — a security researcher's "patch gap" analysis (cited in search results) argues the isolation boundary is strong against the renderer-escalation class of bug but is not an absolute guarantee against all exploitation paths. This is a caveat on the strength of the isolation, not a reason to question the recommendation itself.

## 3. worker_threads vs utilityProcess for DB-query execution

**Mechanics, both confirmed directly from Electron's own `utility-process` docs (fetched):** `utilityProcess.fork()` spawns a process via Chromium's internal Services API (Electron's docs describe it as the `child_process.fork` equivalent built on that API rather than Node's own process-spawning machinery), running a full Node.js environment, communicating via `process.parentPort`/`child.postMessage` with transferable `MessagePortMain` objects — including, per Electron's `MessagePorts in Electron` tutorial, the ability to hand one end of a channel directly to a renderer after the main process brokers the initial handshake, so that subsequent traffic between a utility process and a renderer does not round-trip through main. `utilityProcess.fork` has a documented hard constraint: it "can only be called after the `ready` event has been emitted on `App`." `worker_threads` is Node's own same-process threading primitive; each worker gets its own V8 isolate but shares the host OS process.

**Crash containment — this is the clearest, best-evidenced difference found. High confidence.** The general process-vs-thread fault-domain principle (OS-enforced separate address space per process vs. shared address space per thread) is textbook and uncontested. Applied concretely: multiple independent reports describe a native-level crash or abort (segfault, V8/Chromium `std::terminate`, assertion failure) inside a `worker_threads` worker taking down the entire host Electron process, because the worker shares the main process's OS-level fault domain — this was described for a native parser (tree-sitter) and for an ONNX/VAD inference worker in two separate unrelated projects' issue trackers, and matches Electron's own `utilityProcess` docs positioning that API explicitly for "crash prone components which would have previously been hosted in the main process." A `utilityProcess` crash, by contrast, is isolated at the OS level the same way any Electron child process (renderer, GPU process) is; Electron's crash-reporter docs note utility processes are automatically monitored and produce their own minidumps, giving them first-class crash diagnostics a same-process worker does not get. One nuance confirmed from a 2025 Electron PR (#45921): Electron separately changed *JS-level* unhandled-rejection behavior so utility processes no longer crash by default on an unhandled promise rejection (previously Node's default) — this is an orthogonal, JS-exception-level policy change, not a statement about native-crash containment, and the PR shows this was a deliberate, debated behavior change as recently as 2025.

**Overhead — confirmed directionally, not precisely quantified. Medium confidence.** Each `worker_threads` instance loads a near-complete separate Node.js native library/runtime; community-reported Node core issues (not Electron-specific) describe per-worker overhead in the range of several MB at minimum, with some reports of memory roughly doubling or tripling versus single-threaded equivalents for CPU-heavy workloads, and in one report an "empty" worker consuming nearly as much memory as the entire main process. `utilityProcess` carries the same category of overhead (full separate Node environment) plus full OS-process creation cost rather than just a V8-isolate-within-a-process cost; Electron has been actively reducing utility-process/child-process startup latency (an Electron changelog entry, surfaced in search, notes startup-time improvements to `utilityProcess.fork()`/`child_process.fork()` and adds that some platforms now start processes from an embedded Node.js startup snapshot) — i.e., this is an active, moving target rather than a fixed, settled number, and no source found gives a precise current per-instance MB/ms figure for either API that could be cited with confidence.

**Sustained-use stability — the prior finding is confirmed and should be sharpened, not softened. Medium-to-high confidence.** The most specific, most recent evidence found is **electron/electron#47986**: an open, unresolved 2025 issue reporting that after roughly 10 minutes of runtime, an app using `worker_threads` crashes with a native assertion failure tied to `PerIsolatePlatformData` destruction during worker-thread teardown — reported as a regression present on Electron 37.2.6 that was not present on 35.7.4. This is a more specific and more current data point than the prior task finding's generic "community reports of stability issues under sustained heavy use," and it points at worker *teardown*/lifecycle specifically (not just steady-state memory growth) as a trigger. Independently, plain Node.js core has a long-running, multi-year (2019 through at least 2023) series of open `worker_threads` memory-growth/leak issues (nodejs/node #27844, #27998, #29784, #32265, #34823, #40878, #45685) describing compiled-code memory and per-worker overhead not being reclaimed after termination — this is a separate, longer-standing, non-Electron-specific body of evidence that independently corroborates "don't assume `worker_threads` behaves cleanly under sustained heavy use," though these are scattered individual GitHub issue reports rather than a vendor-acknowledged defect, and most are several years old. No comparably specific sustained-use stability complaints against `utilityProcess` were found in this research, though `utilityProcess` is a newer API — Electron's own PR introducing it (#34980) was merged October 20, 2022 — with a correspondingly shorter real-world track record than `worker_threads` to draw negative reports from; absence of reports is not strong evidence of absence of issues.

## 4. Multi-tab/multi-connection concurrency

**Cancellation is SDK/driver-level in both providers and does not require process-level kill — confirmed, high confidence, but the two providers differ materially in what cancellation actually does:**

- **Azure SQL (`mssql`/`tedious`):** the `mssql` package's own docs describe `Request.cancel()` as: *"Cancel currently executing request. Return `true` if cancellation packet was send successfully"* — surfacing an `ECANCEL`/`RequestError` ("Cancelled.") to the client on success. Cross-referencing this against the underlying protocol: the `tedious` driver internally tracks an `attentionSent` state, and Microsoft's own MS-TDS protocol specification defines the **Attention** message as the mechanism a client sends to interrupt a request already fully sent to the server, after which the client must wait for an attention acknowledgment — i.e., the wire-level mechanism `mssql`'s "cancellation packet" sends is TDS's Attention signal, which the spec describes as actually interrupting server-side execution of the request, not merely a client-side abandonment. **High confidence** this is genuine server-side cancellation (not just client-side abandonment), based on the protocol spec plus the driver's own internal naming; this can be wired to a standard `AbortController`/`AbortSignal` by registering an `abort` listener that calls `request.cancel()`.
- **Cosmos DB (`@azure/cosmos`):** query methods accept an `abortSignal` (standard `AbortSignal`) in `FeedOptions`, and calling `controller.abort()` cancels all in-flight requests for that query call — including, per Microsoft's own docs, every parallel per-partition fan-out request in a cross-partition query. However, multiple Azure SDK sources (Microsoft's own abort-signal blog post and docs) are explicit that **this is a client-side abandonment of the request, not a cancellation signal sent to the service** — in Microsoft's own general framing (given for Key Vault but stated as a general Azure-SDK abort-signal property), the operation may complete server-side regardless; for Cosmos specifically this means RU charges already incurred for in-flight partition requests are not undone by `abort()`.

This asymmetry (true server-side cancel for SQL vs. client-side abandon for Cosmos) is a concrete, provider-level fact relevant to a "cancellable tab" requirement, and it is unaffected by whether execution happens in main, a worker, or a utility process — in all three placements, cancellation is "call the SDK's own abort method," not "kill the thread/process."

**Per-tab vs. shared-pool architecture — a concrete, process-model-relevant cost of per-tab isolation was found for the SQL Server driver, confirmed, high confidence in the mechanism (not independently load-tested here).** `mssql` manages connections via a `ConnectionPool` object, and pooling is per-`ConnectionPool`-instance. If each tab were given its own `worker_thread`/`utilityProcess`, each such instance would need its own `ConnectionPool`, meaning N tabs against the same Azure SQL server would open N independent connection pools rather than sharing one — a direct architectural cost (more server-side connections, more handshake/auth overhead, pool-sizing tuning multiplied by tab count) that is specific to choosing per-tab process/thread isolation over a shared in-process (or shared-worker) connection/pool layer. This was not found addressed in any source for Cosmos DB (whose SDK does not use a comparable connection-pool abstraction — it is HTTP/TCP-connection-pooled internally by the SDK's own transport layer), so the finding above is confirmed specifically for the SQL Server provider, not generalized to Cosmos.

**On whether running directly in main is "sufficient" given point 1's finding that async I/O itself never blocks anything:** no source found directly addresses "is main-process-only execution sufficient for N concurrent cancellable query tabs" as a stated question — this is a synthesis point, not a sourced fact, and is left for the human decision rather than asserted here. What the above sections do establish as facts bearing on that decision: (a) the query I/O itself is not a reason to isolate; (b) the CPU-bound JSON-processing step around large result sets is a reason some isolation *might* help, but only on the main-process side of the pipeline — it does nothing for the independently-blocking renderer-side deserialization cost (§1); (c) per-tab process/thread isolation has a confirmed, concrete cost for the SQL Server provider in the form of fragmented connection pooling; (d) cancellation itself works identically regardless of where execution is placed.

**Confidence notes:** Direct quotes from Electron's own process-model, performance, and utilityProcess docs (fetched in full) are **high confidence** — primary-source, current as of this research. The security baseline (`contextIsolation`/`nodeIntegration`/`contextBridge`/`sandbox`) is **high confidence** — multiple independent 2025 sources converge with no disagreement found. The decomposition of "freezes the UI" into renderer-paint/input-dispatch/IPC/OS-ANR effects is **mixed confidence** — IPC-stalling and OS-ANR are well-supported; renderer-paint and input-dispatch claims rest on older (2015-2017) community issues not independently re-verified against current Electron internals, and are flagged as such above. The worker_threads-crash-takes-down-main-process claim is **high confidence** as a general process/thread fault-domain principle and is corroborated by Electron's own utilityProcess docs positioning plus one specific, recent (2025), still-open Electron regression report (#47986); several of the supporting anecdotes are single-project GitHub issues and are labeled as such rather than treated as broad consensus. The mssql-vs-Cosmos cancellation asymmetry (server-side attention packet vs. client-side abandonment) is **high confidence**, sourced from the `mssql`/`tedious` drivers' own documented behavior, Microsoft's own MS-TDS protocol specification for the Attention message, and Microsoft's own Azure SDK abort-signal documentation. Per-tab connection-pool fragmentation for `mssql` is **high confidence** in mechanism (pooling is documented as per-`ConnectionPool`-instance) but **not independently load-tested** in this research. Overhead/memory figures for `worker_threads` and `utilityProcess` are **medium confidence** — directionally consistent across multiple sources but no precise, current, authoritative benchmark was found for either, and Electron's own process-startup performance work is actively ongoing, meaning any number found risks being stale quickly.
