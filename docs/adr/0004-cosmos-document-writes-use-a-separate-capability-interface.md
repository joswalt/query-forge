# Cosmos Document Writes use a separate capability interface, not the Database Provider Interface

The Cosmos query language is SELECT-only, so writing to Cosmos (the Cosmos writes map, `.scratch/queryforge-cosmos-writes/`) can't go through `executeQuery` the way Azure SQL's `INSERT`/`UPDATE`/`DELETE` statements do. Every change is a **Document Write** (GLOSSARY.md): one create, replace or delete of a single document, addressed by `id` and partition key value through the SDK's point operations.

We left the locked Database Provider Interface (spec.md) unchanged and added a Cosmos-only capability interface, `DocumentWriter`. The Cosmos DB Provider implements it alongside `DatabaseProvider`. The Query Execution Service checks a provider for the capability before dispatching a new `writeDocument` protocol request, and refuses the request on a read-only Connection Profile before the provider is touched, the same boundary `assertReadOnlyQuery` holds for Azure SQL. A Document Write is one discriminated union (`create | replace | delete`) through one method, so bulk DML can later send many through the same path. Replace and delete always carry an explicit partition key, because `@azure/cosmos` silently targets the None key when one is left out. Expected outcomes come back typed (`conflict`, `precondition-failed`, `not-found`, each with `requestCharge`) instead of as errors, and Document Writes can't be cancelled: Cosmos cancellation only abandons the request on the client side, which would leave the outcome unknown.

**Considered and rejected**: (a) optional `writeDocument?()` on `DatabaseProvider`: simpler wiring, but it puts a Cosmos-shaped method on the engine-neutral contract that Azure SQL will never implement; (b) a separate writer component sharing the Provider's `CosmosClient`: gives the live client two owners, against "a Database Provider owns its own connection pool".

**Amendment (2026-11-03, Editable rows)**: `DocumentWriter` also carries `readDocument({ id, partitionKey, database?, container? })`, a point-read returning the document plus `requestCharge`, or a typed `not-found`. Edit and Delete read the full document before opening the editor, so an edit never starts from a partial projection. It is a read, not a Document Write, so the read-only refusal does not apply to it.

**Amendment (2026-11-03, Concurrency and conflicts)**: `ifMatch` is required, not optional, on replace and delete Document Writes, so no write can silently overwrite a newer version (a **Concurrent Change**, GLOSSARY.md). The etag comes from the edit session's `readDocument` response (then from each successful replace's returned document), never from the `_etag` in the edited body. "Overwrite" after a Concurrent Change is a fresh `readDocument` followed by a replace with that etag, reachable only from the compare view; there is no unconditional replace or delete, and no "delete anyway".
