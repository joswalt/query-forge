# Cosmos Document Writes use a separate capability interface, not the Database Provider Interface

The Cosmos query language is SELECT-only, so writing to Cosmos (the Cosmos writes map, `.scratch/queryforge-cosmos-writes/`) can't go through `executeQuery` the way Azure SQL's `INSERT`/`UPDATE`/`DELETE` statements do. Every change is a **Document Write** (GLOSSARY.md): one create, replace or delete of a single document, addressed by `id` and partition key value through the SDK's point operations.

We left the locked Database Provider Interface (spec.md) unchanged and added a Cosmos-only capability interface, `DocumentWriter`. The Cosmos DB Provider implements it alongside `DatabaseProvider`. The Query Execution Service checks a provider for the capability before dispatching a new `writeDocument` protocol request, and refuses the request on a read-only Connection Profile before the provider is touched, the same boundary `assertReadOnlyQuery` holds for Azure SQL. A Document Write is one discriminated union (`create | replace | delete`) through one method, so bulk DML can later send many through the same path. Replace and delete always carry an explicit partition key, because `@azure/cosmos` silently targets the None key when one is left out. Expected outcomes come back typed (`conflict`, `precondition-failed`, `not-found`, each with `requestCharge`) instead of as errors, and Document Writes can't be cancelled: Cosmos cancellation only abandons the request on the client side, which would leave the outcome unknown.

**Considered and rejected**: (a) optional `writeDocument?()` on `DatabaseProvider`: simpler wiring, but it puts a Cosmos-shaped method on the engine-neutral contract that Azure SQL will never implement; (b) a separate writer component sharing the Provider's `CosmosClient`: gives the live client two owners, against "a Database Provider owns its own connection pool".

**Amendment (2026-11-03, Editable rows)**: `DocumentWriter` also carries `readDocument({ id, partitionKey, database?, container? })`, a point-read returning the document plus `requestCharge`, or a typed `not-found`. Edit and Delete read the full document before opening the editor, so an edit never starts from a partial projection. It is a read, not a Document Write, so the read-only refusal does not apply to it.

**Amendment (2026-11-03, Concurrency and conflicts)**: `ifMatch` is required, not optional, on replace and delete Document Writes, so no write can silently overwrite a newer version (a **Concurrent Change**, GLOSSARY.md). The etag comes from the edit session's `readDocument` response (then from each successful replace's returned document), never from the `_etag` in the edited body. "Overwrite" after a Concurrent Change is a fresh `readDocument` followed by a replace with that etag, reachable only from the compare view; there is no unconditional replace or delete, and no "delete anyway".

**Amendment (2026-11-05, Bulk DML syntax and translation)**: the Document Write union gains `patch`: `{ kind: 'patch', id, partitionKey, ifMatch, operations, database?, container? }`, with `ifMatch` required as on replace and `operations` limited to `set` and `remove` (at most 10, the service cap). A **DML Statement** (GLOSSARY.md) `UPDATE` becomes one patch per matching document, with values computed server-side by the **Driving Query** projection, so the patch sends only the changed properties and QueryForge needs no expression evaluator. Single-document Edit keeps using replace. Rejected: read-and-replace for `UPDATE` (no union change and no 10-assignment cap, but every write ships the whole document and the Driving Query must return full documents); `incr` and `add` (a projected value plus `ifMatch` already covers them safely).

**Amendment (2026-11-05, Bulk DML execution semantics)**: a DML run is two protocol requests around a held **DML Plan** (GLOSSARY.md). `planDml` re-parses the statement, refuses on a read-only profile, runs the Driving Query to the end (at most 50,000 matches) and keeps the plan in the Query Execution Service; `commitDml` writes exactly that plan, so the user confirms the documents and versions that will be written, and anything changed in between fails as a Concurrent Change. `discardPlan` drops it. Commit sends point Document Writes through `writeDocument` from a fixed pool of 8, streaming one **Write Outcome** per document as Result Chunks. Unlike a single Document Write, a DML run is cancellable by Execution ID: cancel stops dispatching, lets in-flight writes finish so their outcome is known, and leaves the rest not attempted. Rejected: `executeBulkOperations` (bulk delete ops have no typed `ifMatch`, results arrive only when every op settles, and abort still dispatches queued batches and can leave an aborted batch committed); `items.batch` (atomic only within one partition, so one Concurrent Change fails up to 99 neighbours with 424, while the run is still not atomic overall); re-selecting at commit instead of holding a plan (the documents written could differ from what was confirmed).

**Amendment (2026-11-13, Retry failed after a DML run)**: after `commitDml` ends, the Query Execution Service keeps the tab's **last committed run** (statement text, database/container, and each document's address with its Write Outcome; no `SET` values), replaced only when another run in the tab commits and dropped by a plan for an ordinary statement, disconnect or tab close. A new request `planRetry { planId, executionId }` builds a **Retry** (GLOSSARY.md): it refuses on a read-only profile, takes the run's documents that did not end `written` or `unchanged`, and re-runs the Driving Query restricted to their addresses, so `WHERE`, `SET` values and `_etag` are evaluated against current versions and the result is an ordinary DML Plan (same result shape as `planDml` plus `scopeCount`), committed with the unchanged `commitDml`. The restriction runs in chunks of at most 1,000 addresses and 256 KB (`c.id IN (…)` plus each partition key path `IN (…)`, with a `NOT IS_DEFINED` branch for the None value), keeping only exact address matches, because Cosmos caps query text at 512 KB and every query costs about 2.5 RU per physical partition touched. Rejected: no retry (re-running the statement re-matches the whole container, applies non-idempotent `SET`s twice and re-emits already-written documents on the change feed); a renderer-built statement with an address list (megabytes of text at the ceiling, editable scope, bloats Query History); reusing the held plan's values (a Concurrent Change can only be retried by re-reading); one query per partition key value (at least ~125k RU for 50,000 distinct keys); an optional `retryOf` on `planDml` (conditionally required fields).
