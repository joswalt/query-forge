# Renew Entra ID access tokens mid-session by asking main over the MessagePort

ADR 0001 hands a Decrypted Secret to the Query Execution Service once per `connect()`. For Entra ID and service principal profiles that secret is an access token that lives about an hour, while a connection can live all day: an Azure SQL pool that reconnects (or opens a new physical connection) after the token expired fails its login, and a Cosmos client starts getting 401s. The first version surfaced "disconnect and reconnect" and left it there.

The utilityProcess cannot mint tokens itself: the MSAL token cache is Secret Ciphertext (decryptable only in main), and a service principal's client secret must never leave main. So the utilityProcess asks main. A Provider that was given a `SecretRefresher` at `connect()` calls it when it needs a token newer than the one it holds; the Query Execution Service sends `{ kind: 'refreshSecret', id, profileId }` to main, main renews the token and answers with `{ method: 'refreshSecretResult', id, secret | error }`. Azure SQL uses tedious's `token-credential` authentication (tedious asks for a token on every login), Cosmos uses its `aadCredentials.getToken`, and both read the token's `exp` claim and renew five minutes early (`RefreshingTokenSource`).

**Renewal is silent only.** `ConnectionManager.refreshSecret` never opens a browser: a service principal re-runs its client-credentials exchange, an interactive sign-in uses the cached refresh token (`acquireToken(..., { allowInteractive: false })`). A background pool login must not pop a sign-in window unprompted. When silent renewal fails, the Provider surfaces a `TokenRefreshError` — "could not be renewed ... disconnect and reconnect to sign in again" — so reconnecting (which may open the browser, by the user's choice) remains the recovery path.

**Considered and rejected**: (a) main pushing a new token to the utilityProcess on a timer — main would renew tokens for connections nobody is using, and a Provider still needs a way to wait for a token that is expiring right now; (b) giving the utilityProcess the refresh token or client secret — breaks ADR 0001's core property that long-lived credentials stay in main; (c) letting renewal fall back to an interactive sign-in — a surprise browser window from a background login.

**Consequence**: this amends ADR 0001's "once per connect ... never re-transmitted". A short-lived *access token* now crosses main→utilityProcess again each time it is renewed, over the same internal channel and with the same handling (never logged, never persisted, never sent to the renderer). Long-lived credentials (passwords, account keys, client secrets, refresh tokens) still cross at most once or not at all. Test Connection's throwaway pool/client gets no refresher and keeps the single token (`azure-active-directory-access-token`).
